Использует архитектуру LSM Tree.
Преимуществом Bbolt является то, что он не так активно использует оперативную память, он подгружает только те части базы, которые необходимы в аднный момент. Но здесь нет шифрования из коробки, нужно писать обёртку.

Следующая задача - реализация нормального шифрования кэша, без заглушки. Самым простым способом будет шифрование на основе пароля.
Важный момент: Для аутентификации на сервере используется bcrypt так как он устойчив к перебору. Однако если использовать зашифрованный пароль, не получится открыть базу на клиенте второй раз, так как бкрипт каждый раз выдает разные строки.

Есть два основных варианта отправки файлов:
1. Засунуть весь файл в один пакет. Минусы: если файл будет большой, приложение зависнет пока будет его отправлять, сервер может разорвать соединение из-за слишком большого пакета.
2. Чанкинг. Разбить файл на маленькие кусочки и отправлять. В этом случае чат не блокируется.
Я выбираю второй вариант, так как он наиболее правильный.
Теперь нужно решить, как программа будет проверять, что файл верно отправился. Из вариантов я рассматриваю:
1. метод счетчика.  Просто сверять в конце передачи количество байтов. это наиболее простой вариант
2. финальный пакет. после отправки последнего чанка отправлять последний пакет со специальным типом.
3. Контрольная сумма. - по сути единственный способ проверить, что файл пришел целиком и не повредился по пути.
Перед отправкой файл прогоняется через алгоритм хеширования, эта строка добавляется в заголовок, на стороне получателя считается хеш файла, если два хеша совпали, то файл передался без ошибок.
Этот вариант мне нравится больше остальных, так как он наиболее точный и "профессиональный".

В ходе тестирования работы было выявлено несколько проблем:
1. логи от передачи файлов попадают в общие,
2. Кэш восстаналивает удаленные переписки
3. При выходе из переписки, сообщения из нее не приходят даже если её восстановить.
4.Самая критичная проблема: Грейсфул шатдаун работает некорректно при нескольких пользователях в сети.
Суть проблемы с грейсфул шатдаун:
горутины клиентов пытаются записать лог о выходе уже в тот момент, когда main() уже выполнил закрытие базы данных.
Из-за этого возникает ошибка доступа в базу. Это произошло из-за неправильного использованя вэйтгруппы. Сервер должен закрывать базу только тогда, когда абсолютно все горутины завершились.

Другой ранее упущенной проблемой было то, что при повторном заходе дублировалась история сообщений из кэша и из базы данных. Для решения был применен простой алгоритм:
при получении или отправки сообщения обновляется время последней синхронизации. при повторном заходе в клиент из базы данных в клиент выводятся только те сообщения, что были добавлены в базу после времени последней синхронизации.
